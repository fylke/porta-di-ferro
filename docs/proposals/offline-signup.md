# Feature Proposal: Offline Event Signup

> **Implemented** (issue #91), with staff signup from issue #5 added to it. The formats
> and the rules are `internal/signup`, the endpoints are `internal/http/signup.go`, the
> participant app is `web/signup/signup.html`, and the organizer's screen is
> `web/src/routes/Signup.svelte`. Where the built thing differs from this proposal, the
> differences are listed at the bottom under "What was built", and the way from here to
> an online signup is under "Towards online signup".

## Summary

Add an offline signup workflow for events that run several disciplines. The organizer
publishes a small JSON definition file. A participant opens that definition in a standalone
signup app, sees the disciplines and event schedule, chooses one or more disciplines, and
exports a response JSON file. The organizer imports the response files into Porta di Ferro
after reviewing them.

This keeps registration possible without an internet-facing server, accounts, or a shared
database.

## Scope

The first version supports:

- An event name, venue, date, and organizer-facing event identifier.
- A list of available disciplines or tournament instances.
- The order and start time of each discipline.
- Breaks such as lunch, with a start and end time.
- Participant name, club and email address.
- Selecting one or more disciplines.
- Exporting and importing JSON files.
- Import preview, validation, duplicate detection, and explicit confirmation.

The schedule describes the event programme. It does not assign individual matches or produce
personalized competitor schedules.

## User Flow

### Organizer

1. Configure the event and the discipline instances in the organizer UI.
2. Enter the discipline order, start times, and breaks.
3. Download the signup definition file.
4. Send the file and the signup app to participants by email, USB stick, or any other channel.
5. Import one or more participant response files.
6. Review additions, duplicates, validation errors, and capacity warnings.
7. Confirm the import to add competitors to the selected tournament instances.

### Participant

1. Open the standalone signup app locally in a browser.
2. Load the organizer's definition file.
3. Read the event information and schedule.
4. Enter their details and select disciplines.
5. Export a response file.
6. Return that file to the organizer.

The signup app should work from a static offline bundle. It should not depend on a service
worker, HTTPS, or a running Porta di Ferro server. This is important because most venue clients
use an insecure LAN origin.

## File Formats

The formats are separate from the results export. Results describe a completed tournament;
signup files describe a proposed registration.

### Definition

```json
{
  "format": "porta.signup",
  "version": 2,
  "definitionId": "msl-open-2026",
  "event": {
    "name": "MSL Open",
    "venue": "Linkoping",
    "date": "2026-11-15"
  },
  "schedule": [
    {
      "type": "discipline",
      "label": "Longsword pools",
      "startsAt": "09:00"
    },
    {
      "type": "break",
      "label": "Lunch",
      "startsAt": "12:00",
      "endsAt": "13:00"
    }
  ],
  "tournaments": [
    {
      "id": "open-steel-longsword",
      "label": "Open Steel Longsword",
      "capacity": 28,
      "startsAt": "09:00"
    }
  ],
  "fields": ["name", "club", "email"]
}
```

The definition contains stable tournament identifiers, not process ports or filesystem paths.
That lets the organizer regenerate a definition without exposing local implementation details.

### Response

```json
{
  "format": "porta.signup.response",
  "version": 2,
  "definitionId": "msl-open-2026",
  "submittedAt": "2026-09-21T12:00:00Z",
  "participant": {
    "name": "Ada Example",
    "club": "Example HEMA",
    "email": "ada@example.org"
  },
  "entries": ["open-steel-longsword"]
}
```

The response must retain the definition identifier so an organizer cannot accidentally import
a response into the wrong event. The server should still require explicit confirmation before
writing imported competitors.

## Proposed Implementation

### Backend

Add an `internal/signup` package containing:

- Versioned definition and response types.
- Structural validation and supported-version checks.
- Required-field and tournament-id validation.
- Duplicate detection within one import and against existing competitors.
- Capacity checks as warnings or errors according to organizer policy.

Add organizer endpoints for:

- Downloading the current signup definition.
- Previewing imported response files without changing tournament data.
- Confirming a validated import.

The import operation should be idempotent when the same response is submitted twice. It must
not silently create a second competitor. Name and club are not sufficient as a universal identity,
so the response should carry a stable submission identifier generated by the signup app.

### Frontend

Add organizer controls for event metadata, schedule rows, breaks, and signup-definition export.
Add an import screen with a preview table showing:

- New registrations.
- Existing or duplicate registrations.
- Unknown tournament identifiers.
- Missing or invalid fields.
- Capacity warnings.

Build the participant app as a static route or bundle that uses file upload/download and local
browser storage only. It should share the project's translation and validation conventions where
practical, but it must remain usable without the organizer server.

### Data model

The existing competitor record can remain unchanged for the initial version. Imported entries
map to existing tournament instances and create ordinary competitors through the same store
path as local registration. Event metadata and signup configuration should be stored separately
from match results so the existing append-only match log remains unaffected.

## Acceptance Criteria

- An organizer can create and download a definition for an event with multiple disciplines.
- The definition displays discipline times and breaks, including lunch, offline.
- A participant can complete a signup without internet access or a running server.
- The participant can select more than one discipline when permitted.
- The participant can export a response JSON file and reopen it for inspection.
- The organizer can preview a response before importing it.
- Invalid, stale, duplicate, and unknown-discipline responses are clearly reported.
- Re-importing the same response does not create duplicate competitors.
- Confirmed imports appear in the normal competitor and tournament views.
- Existing results export, match scoring, and offline scorekeeper behavior are unchanged.
- No service worker or secure-context-only API is required by the participant app.

## Deliberate Non-Goals

- Public web registration or payments.
- A central registration database.
- Personalized match schedules.
- Automatic timetable generation.
- Live synchronization between participant apps and the organizer.
- Replacing the existing completed-results export.

Personalized scheduling remains a separate future feature. This proposal only publishes the
organizer's event programme: when disciplines run and when breaks occur.

## What was built

The places where the built feature differs from the proposal above, each deliberate:

**The disciplines are the definition** (version 2, #142). What can be entered is the
event's disciplines themselves, by their address in the event and their name, each with
its capacity (set in the discipline's setup) and when the plan has it starting. The first
version listed rows of the programme marked as disciplines, and each discipline then had to
be matched to a row; nothing needs matching now, and a discipline is entered under the one
name it has everywhere else. The programme still goes out, to read. Version 1 files are
refused with a reason: none were sent out for real.

**Everybody gives an email** (version 2, #142). It replaces the optional contact field, and
it is an identity rather than a detail: the person it belongs to keeps it in `people.json`,
never in anything the hall can open, and a second response with the same address -- from
another device, so with another submission id -- is the same person. Where they are
already entered it is `already`; where they are not, it is a new entry of the same
person. Two people who share a name but not an address are never offered to the organizer
as maybe the same person. Nothing confirms the address by mail: the server runs offline at
the venue.

**One file goes out, not two.** `GET /api/signup/app.html?download=1` returns the
participant app with the event written into it, so the organizer sends a single
attachment. `GET /api/signup/definition.json` is still there for anyone who wants the two
files separately, and a bare copy of the app asks for a definition. "Open both of these,
the second one from inside the first" is an instruction people get wrong.

**Each discipline imports its own.** One import on the event's page gives every discipline
the responses naming it, through the same check each runs on its own (issue #102);
responses for a discipline the event does not have are reported as such.

**Staff sign up in the same file.** The proposal covers participants only. A response can
also offer to work, as `"staff": {"tournaments": [...], "roles": [...]}`, and the
definition publishes the roles to choose from — head referee, assistant referee, score
keeper, physician — with whether the app ticks each by default. Everyone is down for
every discipline they are not fencing in, in every role but physician, and unticks what
they would rather not do: asking people to volunteer finds fewer staff than letting them
opt out. The app never offers a discipline they have entered, and the import drops such
an offer from a hand-edited file. Each discipline takes the offers naming it, as with entries,
into `Tournament.Staff`. Assigning them to mats and pools is the rest of issue #5.

The submission identifier the proposal asks for is generated by the participant app with
`crypto.getRandomValues` — not `crypto.randomUUID`, which needs a secure context that a
file in a downloads folder does not have. It is stored on the imported competitor as
`Competitor.Signup`, which is what makes a second import a no-op.

## Towards online signup

The offline route is not a stopgap for an online one to replace. It stays, and an online
signup should be built out of it rather than beside it, so that a truly offline event
keeps working from start to finish.

- **The response file is the contract.** Whatever collects signups — email and a folder
  today, a web page later — produces the same `porta.signup.response` and hands it to the
  same `signup.Check`. The duplicate rule, the split by discipline and the preview before
  anything is written all come along without being written twice.
- **The participant app is the same app.** It builds the response in one pure function
  and sends it through one other, `deliver()`. Offline, `deliver()` saves a file. The
  baked file already works unchanged as a page on a club's website, with answers coming
  back by email; giving `deliver()` a server to post to is the one change that makes the
  answers arrive on their own, with saving a file kept as the fallback.
- **The organizer's side needs one way in, not a second import.** A receiving server
  would keep each posted response as a file and hand the folder to the import as it
  stands, or pass the bodies straight to `Check`.

What that would take is somewhere reachable from the internet to receive responses —
which this project deliberately does not need, so where it lives is the organizer's
choice — a receiving address in the definition beside the event, and `deliver()` posting
to it.
